# P0 模块演进初步规划

> 状态：draft；本文只定义演进方向和决策门槛，不授权执行目录迁移、拆仓、删除历史资料或改变对外行为。

## 1. 目标与当前决策

`tu-devkit` 继续作为 P0 的聚合仓，维护三个相互关联但边界清晰的能力域：

- `ai-guidance/`：跨仓库 AI 上下文、公共规则、产品知识与团队工作流 Plugin。
- `dev-env-init/`：面向开发者的 `tu` 开发环境初始化与诊断工具。
- `vps-init/` 与 `docs/vps/`：VPS 初始化脚本、配置模板和运行维护知识。

当前不拆分为独立仓库。优先解决模块内部的职责落位、历史资料归档和可复用运维脚本的正式化，避免在没有独立版本、维护者或权限边界时增加发布与协作成本。

## 2. 演进原则

1. **保持用户入口稳定。** `tu` 命令、VPS 安装入口、`ai-guidance/AGENTS.md` 和已发布的文档链接在演进期间应保持兼容；需要调整时先提供迁移说明与回退路径。
2. **按职责迁移，不按文件数量迁移。** 只有明确属于某个模块的实现、文档或测试才移动；不为目录整齐而重排稳定资产。
3. **可执行资产与运行产物分离。** 可长期复用的脚本进入正式脚本目录并有测试；一次性诊断、脱敏前输出和环境生成物不进入受版本控制的功能模块。
4. **Plugin 只承载可重复执行的工作流。** 公共规则与产品事实继续留在 `ai-guidance/core/`、`ai-guidance/products/`；只有触发边界明确、跨任务复用的流程才进入团队 Plugin。
5. **拆仓以独立生命周期为前提。** 发布节奏、权限边界、维护责任、消费者和 CI 都能独立时，才评估独立仓库。

## 3. 模块规划

| 能力域 | 近期定位 | 近期动作 | 暂不做的事 |
| --- | --- | --- | --- |
| `ai-guidance/` | P0 的共享上下文与工作流分发中心 | 继续按 `core/`、`products/`、`plugins/` 分层；新增工作流先判断是否满足 Plugin 化门槛 | 不把所有 Markdown 规则直接转为 Skill 或 Plugin |
| `dev-env-init/` | 独立安装、但仍在 P0 统一维护的 CLI 工具 | 将 `scripts/bootstrap.sh` 中按能力划分的安装逻辑逐步迁入 `modules/<name>/`；Profile 与 `tu` 路由保持不变 | 不改变 Profile 名称、默认组合或安装副作用 |
| `vps-init/` | VPS 声明式初始化、生成模板与受控脚本 | 将被确认可复用的运维/诊断脚本纳入 `scripts/` 或 `tests/`；保留 `docs/vps/` 作为运行维护知识入口 | 不将本机 `output/`、密钥、端点或临时排障材料提交入库 |
| `docs/superpowers/` | 历史方案来源，而非当前功能说明 | 建立归档/保留规则，标明已完成、已替代或仍有效的内容 | 不把旧计划当作当前实现契约 |

## 4. 分阶段计划

### 阶段 A：边界整理（近期）

1. 为 `dev-env-init` 定义模块文件契约，例如每个模块的安装函数、诊断函数、支持平台和测试入口。
2. 以一个低耦合模块为试点，从 `scripts/bootstrap.sh` 迁入 `modules/`；保持 `tu install <module>`、Profile 解析和退出码不变。
3. 盘点 `vps-init/output/`：标为“正式脚本”“历史诊断”或“本机产物”。只有第一类才进入正式目录并补齐脱敏与测试。
4. 清点 `docs/superpowers/`，为仍有参考价值的方案补充状态标识；可迁入归档区，但不在本阶段删除文件。

完成标志：模块职责可由目录与入口文档辨认；试点迁移不改变现有 CLI、配置模板或文档入口。

### 阶段 B：模块化稳固（中期）

1. 按依赖从低到高迁移 `dev-env-init` 的能力实现，并让 `bootstrap.sh` 只承担 Profile 展开和模块调度。
2. 为每个迁入模块补充最小单元/脚本测试，以及 Profile 级回归测试。
3. 在 `vps-init` 中固化重复使用的检查工具，明确输入、脱敏输出、支持环境和非目标。
4. 对 `ai-guidance-workflows` 建立候选工作流清单：重复出现、输入明确、需最小上下文、可验证输出后才实施 Plugin 化。

完成标志：每个 `dev-env-init` 模块拥有明确实现位置与回归测试；运行产物不再被误认为正式工具；Plugin 与 Core 的职责没有重叠。

### 阶段 C：独立化评估（远期，按需触发）

仅在下列条件中至少满足三项，并完成依赖与发布评审后，分别评估 `dev-env-init` 或 `vps-init` 的独立仓库：

- 需要独立版本号、发布节奏或安装分发渠道；
- 有 P0 之外的稳定消费者，且消费者不需要其他 P0 模块；
- 维护责任人、访问权限或安全审查边界独立；
- CI、Issue、发布回滚和兼容性策略能够独立承担；
- 跨模块依赖已收敛为版本化契约，而非相对路径或隐式文档约定。

未满足门槛时，保持 P0 聚合仓；通过目录模块化和文档边界解决复杂度。

## 5. 迁移实施约束

任何实际迁移任务都应先明确：源与目标路径、用户可见契约、调用方、配置兼容策略、回退方式和验证命令。不得在同一任务中同时进行目录迁移、功能重构、默认值调整和文档大改。涉及 VPS、安全、网络或公开配置行为时，需单独评估发布与回滚风险。

## 6. 待决事项

- `dev-env-init/modules/` 的最终脚本接口和加载方式。
- `docs/superpowers/` 的归档目录、保留期限与状态标记格式。
- `vps-init/output/` 现有内容的逐项归类结果。
- 独立仓库的潜在发布方式、版本规范和依赖契约。

这些事项在获得真实消费者、维护和发布需求前保持待决，不以本规划推断为既定实施方案。
