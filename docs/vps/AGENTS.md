# P0-1 VPS 部署与网络协作约束

本文件是 P0-1 中所有 VPS 部署、升级、网络调整、连通性、性能与稳定性问题的 AI 总约束入口。它约束的是工作方法、证据标准、变更门禁与交接质量；具体拓扑、命令和已知故障沿本文链接按需读取，不能用历史文档替代当前运行态核实。

## 1. 生效条件与授权边界

只有同时满足以下条件时，才启用本文的 VPS 专项流程：

1. 用户在当前任务中明确指定 `P0-1`，或在已明确为 `P0-1 VPS` 的同一连续问题中要求继续；
2. 用户明确提出 VPS 部署、升级、迁移、安全配置、网络调整、连通性排查、代理/VPN/DNS/路由/防火墙问题、网络性能或稳定性验证。

以下情形不触发本文：仅因当前工作目录是 P0-1、文本中偶然出现 `VPS`、一般性的 Linux/网络知识问答、与真实 VPS/网络目标无关的仓库开发。维护 `docs/vps/` 本身时仍须读取本文件以保持文档结构和安全边界，但不得因此连接或调整真实 VPS。

触发本文不等于获得任意变更权限：

- “检查、分析、排查、评审”默认只执行只读取证；不得修改 VPS、云防火墙、家庭电脑、路由器、Clash Verge、WireGuard 或外部服务。
- “部署、调整、修复、恢复”只授权实现用户明确目标所需的最小变更；不得顺带升级、加固、换协议、重建 Peer、轮换凭据或改造整条链路。
- 只读检查可覆盖用户目标涉及的端到端链路；实际写操作必须限定到已经说明的端点和组件。需要扩大到其他设备、云控制面或公网入口时，先说明必要性与影响。
- 改 SSH、云/主机防火墙、默认路由、`AllowedIPs = 0.0.0.0/0`、全局 DNS/TUN、密钥/凭据、生产监听端口，或执行可能中断远程连接的服务停止/重启，属于高风险变更；执行前给出精确对象、影响、恢复入口与回滚方案，并取得必要确认。

本文与仓库根 [AGENTS.md](../../AGENTS.md) 叠加使用；指令优先级、工程范围和通用安全要求仍以平台、系统、开发者、用户与本仓库入口为准。涉及 `vps-init/` 脚本或配置实现时，还必须阅读 [`../../vps-init/README.md`](../../vps-init/README.md)。

## 2. 核心原则

### 2.1 以当前有效运行态为事实

事实可信度按任务现场判断，不能把仓库默认值、模板、旧复盘或控制面显示当作当前状态。至少区分：

1. **目标状态**：用户希望形成的拓扑或行为；
2. **声明配置**：仓库、本地文件、服务配置或 UI 中保存的值；
3. **有效配置**：进程实际加载、合并、覆盖后的配置；
4. **运行状态**：监听、路由、连接、握手、流量计数、日志和进程状态；
5. **端到端行为**：目标应用和真实负载经过预期路径后的结果。

声明配置只能证明意图，不能证明已加载；进程存活和本地监听只能证明局部状态，不能证明应用选路或端到端成功。完成结论必须以与用户症状相匹配的运行态和端到端证据收口。

### 2.2 先画实际路径，再定位层次

开始排查前，用一行写出**期望路径**，再根据当前证据写出**实际路径或未知跳点**。例如：

```text
应用 -> 系统代理/TUN -> Clash/Mihomo -> 操作系统路由/WireGuard -> VPS 入站 -> sing-box -> 目标站
```

链路允许按实际组件增删，不能预设所有问题都包含 Clash、WireGuard 或 sing-box。每次只在最早未通过的门禁继续取证，不跨层猜根因：

| 层次 | 必须回答的问题 | 合格证据示例 |
| --- | --- | --- |
| S0 现象与目标 | 哪个应用、请求类型、时间段、成功标准是什么 | 可重复步骤、错误类型、成功率或时延基线 |
| S1 应用入口 | 应用实际使用系统代理、显式代理、TUN、直连还是其他路径 | 应用设置、进程连接、代理日志的同一请求关联 |
| S2 客户端网络 | DNS、路由、接口、系统代理和防火墙如何处理该目标 | 有效系统设置、路由表、解析结果、连接五元组 |
| S3 客户端中间层 | Clash/Mihomo/VPN 等加载了什么，实际选择哪个节点/接口 | 活动 Profile、合并运行配置、Controller/运行态连接 |
| S4 传输/隧道 | TCP、UDP、TLS、WireGuard 等是否建立并双向传输 | 握手、RX/TX、两端同一流量的短抓包 |
| S5 VPS 入站 | 包是否到达，云防火墙、主机防火墙、NAT 和监听是否匹配 | 云规则、`ss`、防火墙规则、入口抓包 |
| S6 服务与出站 | 服务是否加载正确配置并能到达目标 | 配置校验、systemd、受限日志、服务端对照请求 |
| S7 端到端负载 | 原始应用/负载是否稳定通过预期路径 | 多次真实请求、媒体分片/SSE/API 等症状对应验证 |

不适用的层明确标为不适用；无法读取的层标为证据缺口，不得默认通过。

### 2.3 冻结变量，形成因果闭环

- 先保存变更前基线；在没有基线时不连续尝试多个修复。
- 一轮实验只验证一个明确假设，并只改变一个最小变量。必须使用同一探针比较变更前后结果。
- 修改成功后恢复必要的长期配置并验证重载/重启后的持久性；临时命令成功不等于永久修复。
- 实验失败时回滚本轮变量，保留证据，再进入下一假设；不得堆叠未验证修改。
- 发现多个独立故障时分别编号、分别通过门禁，不因最终现象相似而合并成一个根因。

## 3. 任务开始时的最小信息

在执行远程命令或改配置前，先收敛以下信息；能从现场读取的直接读取，不反复询问用户：

- 目标：部署什么，或修复哪个应用的哪类请求；
- 范围：VPS、云控制面、家庭 Windows、路由器、Clash/VPN 中哪些端点在本次范围内；
- 期望路径：直连、系统代理、TUN、分流 VPN、全隧道、私网服务或公网入口；
- 现象：精确错误、首次出现时间、是否稳定复现、页面/API/SSE/下载/视频/UDP 是否表现不同；
- 当前有效状态：活动配置、关键版本、服务、监听、路由、握手和最近变更；
- 成功标准：配置检查、服务健康、握手、业务请求成功率、延迟/吞吐或重启后保持；
- 恢复条件：可用 SSH 会话、供应商 Console、旧配置备份、公网 fallback 或其他带外入口。

时间敏感的证据记录本地/VPS 时间和时区。不同端点时间未同步时，先标明偏差，避免错误关联日志和数据包。

## 4. 证据标准

### 4.1 证据标签

所有重要结论使用以下语义，不混用：

- `verified`：本次任务中由当前配置、运行态、抓包或可重复端到端探针直接证明；
- `observed`：本次稳定观察到现象，但尚未证明原因；
- `inferred`：由多项证据推导出的高概率解释，必须列出推导和仍可能的替代原因；
- `unknown`：当前证据无法判断或权限不可得；
- `historical`：来自旧复盘，只用于提出检查方向，不证明当前故障；
- `target`：用户要求达到的目标状态，不代表现状。

禁止把“命令未报错”“GUI 绿色”“服务 `active`”“TCP 端口能连”“ping 成功”“静态配置通过”“本地代理端口监听”单独表述为整条链路已恢复。

### 4.2 最小证据表

诊断交接至少包含下表字段；简单任务可合并行，但不能省略证据与限制：

| 时间/端点 | 层次 | 命令或探针 | 脱敏观察 | 支持/排除 | 限制 |
| --- | --- | --- | --- | --- | --- |
| `<time> / Windows` | `S4` | `<probe>` | `<result>` | `<claim>` | `<gap>` |

证据必须能对应到同一时间窗口、同一目标、同一端口/协议或同一应用请求。客户端与 VPS 方向性问题优先采集两端对照证据；只看到一端的超时不能定位中间丢弃点。

以下结果不能当作目标层证据：

- 探针本身因权限、TLS 客户端、DNS、Shell 转义或解析脚本失败；
- 缓存结果、旧日志、旧 Profile 或未确认加载的配置；
- 与真实症状不同的协议或负载，例如用首页小请求代表视频分片或长 SSE；
- 只证明公网 fallback 可用，却声称私网主路径可用；
- 只证明 VPS 直连目标成功，却声称家庭电脑经代理路径成功。

### 4.3 根因门槛

称为“根因”至少需要：

1. 证据把故障收敛到明确层次或组件；
2. 最小变更使原失败探针转为成功；
3. 回滚或对照实验能够解释结果差异，或有等价的强因果证据；
4. 相邻层的关键替代原因已被排除；
5. 修复后的真实负载和必要持久性验证通过。

只满足相关性时使用 `inferred` 或“最可能原因”，不得为了给出确定答案而虚构因果。

## 5. 部署、升级与安全变更

### 5.1 实施顺序

部署和升级按以下顺序执行，不从“安装命令跑完”直接跳到完成：

1. 核实目标 Ubuntu/软件版本、官方支持方式和 P0-1 当前脚本能力；版本或上游安装方式可能变化时，以官方资料为准。
2. 检查现有服务、端口、路由、防火墙、磁盘、时间同步和恢复入口，记录变更前基线。
3. 核对本地声明配置，执行 `--dry-run`、语法检查或等价 preflight；不得在输出中暴露 secrets。
4. 备份将被覆盖的配置及其权限/属主，记录精确回滚命令；备份放在受控位置，不提交 Git。
5. 分阶段应用最小变更；每完成一个阶段即验证配置、进程、监听和依赖门禁。
6. 使用 [`../../vps-init/doctor.sh`](../../vps-init/doctor.sh) 或组件原生检查，再执行目标客户端的端到端验证。
7. 验证重载/重启后的运行态、自动启动、规则持久性、fallback 和断开恢复。
8. 只有端到端成功且回滚可用时才报告部署完成。

优先复用 [`../../vps-init/`](../../vps-init/) 的声明式配置、阶段脚本和测试，不在远端临时拼出第二套不受仓库管理的部署流程。仓库没有覆盖的现场修复，应先说明差距，再决定是临时止血还是补入可复用实现。

### 5.2 不得破坏管理入口

- Secure/SSH 迁移必须保留原会话和供应商 Web/Serial Console；新端口、新用户和密钥登录在第二会话中验证成功前，不关闭旧入口。
- 防火墙采用“先允许并验证新路径，再移除旧规则”的两阶段方式；同时核对云安全组、主机防火墙、容器/服务监听，不能只改其中一层。
- 停止 WireGuard、占用当前监听端口、切换默认路由或重启网络栈前，确认当前管理连接不依赖该路径。
- 不通过关闭整个防火墙、允许任意来源、长期开放临时诊断端口或禁用安全机制来制造成功。
- 变更失败、SSH 抖动、关键健康检查失败或结果与预期不符时，立即停止后续阶段并执行预先定义的回滚。

### 5.3 配置与秘密

不得把真实公网 IP、端口组合、私钥、PSK、密码、Token、订阅 URL、Controller secret、Profile ID、客户数据、完整日志或原始抓包写入 Git、文档或聊天。必须展示配置时使用占位符，输出公钥也只在确有诊断必要时最小化展示。

配置修改后先使用组件原生校验器，再 reload；校验失败不得强行 restart。任何生成物都要检查权限、属主、备份位置和 `.gitignore` 边界。

## 6. 通用网络排查纪律

### 6.1 按依赖门禁推进

- 域名失败时区分 DNS 解析、连接建立、TLS、HTTP/应用响应；不能把所有错误统称为“网络不通”。
- TCP 失败时核对解析地址、路由、SYN/SYN-ACK、监听和各层防火墙；UDP 失败必须使用双端同时间窗口证据，不能用 TCP 成功替代。
- VPN 无握手时先处理 Endpoint、监听、密钥/Peer 运行态和双向包；不得提前排查隧道后的 NAT、DNS、Clash 或业务服务。
- 隧道已握手但业务失败时再检查 `AllowedIPs`、策略路由、转发、NAT、MTU、DNS 和目标服务。
- 代理节点健康不等于应用使用了该节点；必须核实节点选择、活动连接和真实请求。
- 公网直连成功不等于代理链成功；代理链成功也不等于所有协议、长连接和大流量稳定。

### 6.2 症状对应真实负载

根据症状选择探针并做多次对照：

- 页面快、视频慢：分别测页面资源、媒体清单和多个媒体分片，核对 QUIC/UDP 443、HTTP/2/TCP、TCP-over-TCP、丢包、抖动、MTU 和持续吞吐；
- API 或 Codex 重试：区分 DNS、TLS、HTTP、SSE/WebSocket、连接复用和长流关闭，记录错误类型而不只记录总耗时；
- 间歇故障：记录时间序列、成功率、P50/P95 或最小可用统计，并关联两端日志/连接变化；
- 性能问题：在同一时间窗口对比直连、VPS 直出、完整代理路径和必要的单变量实验，同时采集 CPU、内存、负载、丢包和重传；没有资源证据时不得归因于“VPS 性能差”；
- DNS 问题：核对应用实际使用的解析器、查询类型、返回地址、Fake-IP/缓存和查询传输路径；单独的 `nslookup` 不能代表浏览器或 TUN 内 DNS。

### 6.3 抓包与诊断工具

- 抓包使用精确接口、目标、协议、端口和短超时，只捕获证明当前假设所需的数据。
- 客户端与 VPS 尽量对同一轮请求抓包；记录发出、到达、响应和返回四个方向，避免只用“有包”下结论。
- Windows 方向问题优先核对物理网卡与虚拟网卡的差异；VPS 同时注意 `any`、公网接口、`wg0`/容器接口的层次。
- 原始 PCAP/ETL 可能包含公网 Endpoint、DNS、SNI 或业务信息，只在受控临时位置分析，任务结束后按用户授权和安全规则清理；文档只保留脱敏摘要。
- 工具返回权限不足、协议栈错误或解析异常时，将其标为工具失败/证据缺口，换独立工具复验；不得把工具错误当作网络结论。

## 7. 协议与组件专项门禁

本节只在实际链路包含对应组件时使用。新协议或新组件仍按第 2、4、6 节的通用门禁处理，不强行套入现有拓扑。

### 7.1 WireGuard

WireGuard 依次通过以下门禁：

1. `W1`：客户端配置可导入，`Endpoint`、Address、公钥方向、PSK 状态、双方 `AllowedIPs` 静态一致；
2. `W2`：Tunnel Service/适配器和 VPS `wg0`/UDP 监听存在；
3. `W3`：两端有近期握手；
4. `W4`：两端 RX/TX 随同一探针双向变化；
5. `W5`：预期私网路由和指定私网地址/服务可达；
6. `W6`：Clash、DNS、全隧道或业务流量按用户目标逐项通过。

`wg-quick@wg0` 的 `active (exited)` 可以是正常状态；GUI 绿色、适配器 Up、仅 TX 增长都不能替代 `W3/W4`。无握手时不进入 NAT、DNS、sing-box 或 Clash。VPS 已收到发起并发出响应而 Windows 物理网卡未收到时，先用同端口普通 UDP 和候选端口做受控对照，不继续围绕密钥发散。完整决策树见 [WireGuard 快速排查](software-guides/wireguard-fast-troubleshooting.md)。

默认先使用 `management` 分流配置验证基础隧道。只有用户明确要求全隧道，且 `W1-W5` 已通过、已准备恢复路径时，才测试 `/0`、DNS、IPv4/IPv6、局域网和 kill switch。不得用全隧道作为无握手问题的基础探针。

### 7.2 Clash Verge / Mihomo

依次核实：系统代理/TUN 是否承接目标应用、活动 Profile、应用级覆盖后的合并配置、节点 `alive/history/interface`、代理组 `now/all`、活动连接和真实请求。`127.0.0.1` 监听、静态 YAML 和 GUI Timeout 都只是局部证据。

当操作系统 WireGuard、私网路由和私网 TCP 已通过，而主 Mihomo TUN 下的节点失败时，先用禁用 TUN、独立端口且不改活动 Profile 的隔离实例验证同一节点；隔离成功后再检查 TUN 出口和设备级 `interface-name`。设备接口名不得直接发布到其他电脑的共享 Profile。完整流程见 [Clash Verge 私网节点排查](software-guides/clash-verge-wireguard-private-node-troubleshooting.md)。

系统代理、TUN 和 Profile 修复必须验证实际合并运行态，并在应用/内核重启后复验；临时注册表写入或直接编辑应用生成文件不能算持久修复。P0-1 检查器按任务需要使用 `-RequireTun`、`-RequireWireGuard`，但静态检查通过不能替代 Controller、连接和真实请求证据。

### 7.3 sing-box 与服务端代理

- 修改前确认当前实际加载的配置路径、版本和 systemd unit；模板不代表运行文件。
- 先运行 `sing-box check` 或对应版本的原生校验，再 reload/restart；随后核对 unit、监听、受限日志和服务端直出。
- 入站 TCP 成功只能证明端口可达；认证、协议、目标出站和长连接需用实际客户端请求验证。
- 客户端/服务端的 TCP、UDP、multiplex、DNS 与路由能力要成对核对；不得只改一端后假定协议协商会自动兼容。
- 日志只读取当前故障窗口并脱敏；不得为了排查开启长期高详细度日志或输出凭据。

### 7.4 防火墙、路由、NAT 与 DNS

同时区分云安全组、VPS 主机防火墙、容器/命名空间规则、服务 bind 地址、转发/NAT 和客户端防火墙。只有数据包到达对应层后，该层规则才进入根因范围。

`AllowedIPs`、策略路由、默认路由和 TUN 规则既可能决定选路，也可能扩大接管范围；修改前后必须保存路由表并检查到管理端、局域网、DNS、VPS 私网与公网 fallback 的影响。禁止通过删除默认路由、全局清空规则或永久关闭防火墙来定位问题。

## 8. 变更协议与回滚

实施每项运行态变更前，简要记录：

```text
对象：<端点/服务/文件/规则>
假设：<本次只验证什么>
变更前：<同一探针基线>
本次只改：<一个变量>
风险：<连接、安全、兼容性影响>
备份/恢复入口：<脱敏位置或方式>
回滚：<精确动作与回滚后验证>
通过条件：<同一探针 + 相邻门禁>
```

变更后按以下顺序验收：配置语法 → 进程/接口 → 监听/路由 → 协议握手/连接 → 双向数据 → 原始失败负载 → fallback/重启持久性。任何前置门禁失败都停止后续验证并回滚或重新取证。

端口迁移、Peer 变更、SSH/防火墙过渡等需要多处同步时，可以作为一个原子变更单元，但必须列出全部对象、正确顺序和失败回滚；不得留下只改服务端或只改客户端的半完成状态。

## 9. 效率与防发散要求

- 首轮优先采集一份客户端、VPS 和目标负载的紧凑运行态快照，再读模板或提出修复。
- 每个假设设定最短可证伪探针；已有证据否定后立即停止该方向，不重复改密钥、重启服务或刷新配置碰运气。
- 解释失败必须指出发生在哪个门禁、下一条证据能区分哪些假设；不得输出没有优先级的“大而全可能原因列表”。
- 新证据与当前假设冲突时，更新结论并显式撤回旧推断，不为维护原判断继续扩展变量。
- 范围外发现只记录影响，不顺带修复。某层已由强证据通过后，不因上层失败返回重做该层，除非出现新的矛盾证据。
- 使用 `ssh tu-vps` 以复用受控 SSH Host 配置；远程脚本包含 `$()`、变量或特殊字符时使用安全引用、stdin 或 Base64，避免 PowerShell 在本地提前展开。
- 在 Windows 从非仓库目录运行 P0-1 工具时使用绝对路径。命令、预期输出和失败分支写入可复用手册，不把一次性运行值写成长期规则。

## 10. 完成标准与交接格式

只有满足下列条件，才能表述“部署完成”“网络已恢复”或“问题已解决”：

- 原始症状已用匹配负载复现，并在变更后用同一方法通过；
- 期望路径的所有适用门禁都有当前运行态证据；
- 已确认实际加载的配置，不只修改了源文件或模板；
- 回滚、fallback、重载/重启持久性按风险完成验证；
- 未引入新的 SSH、DNS、局域网、默认路由或公网 fallback 回归；
- 未验证项、观测窗口和残余风险已明确列出。

最终交接使用以下结构，保持结论先行：

```text
结论：<已解决/部分解决/未解决；根因或最可能原因>
实际路径：<已证实的跳点；未知处标 unknown>
证据：<按端点和门禁列出关键脱敏结果>
变更：<精确对象和单一变量；无变更时明确只读>
验证：<原症状、相邻门禁、重启/持久性、fallback>
回滚：<可执行恢复方式与触发条件>
未验证/残余风险：<权限、时间窗口、外部网络等>
```

没有真实 VPS 或客户端访问权限时，只能声明“仓库配置/文档/静态检查已完成”；不得声称运行态部署或端到端网络已经验证。权限不足时继续完成可用的只读取证，并按公共约束请求授权或交接精确取证命令与预期分支。
